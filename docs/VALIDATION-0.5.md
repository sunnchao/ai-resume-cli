## 新增证据模式的真实接口记录

配置的模型 ID 为 `gemini-3.8-flash`，通过用户现有 Chat Completions 兼容端点访问。只使用 `examples/resume.pdf`、`examples/resume-alt.pdf` 和 `examples/jd.txt`，未读取或发送其他简历。

- `resume.pdf`：首次 HTTP 400，明确再次调用后成功，返回 Schema、分数和原文短引比对通过。
- `resume-alt.pdf`：两次调用均为 HTTP 400，服务方只提供 `Provider API error: bad response status code`，没有可定位的字段或 Schema 错误信息。
- 不据此推断是模型、网关还是请求约束问题。程序保留原有策略：400 不自动重试、不回退 mock；错误被正常转换为退出码 4。
- 第一份结果的通过说明结构与引文存在性检查可运行，不证明所有证据关联和缺口判断都正确。第二份应在端点原因查明后复测。

结构化记录见 [REAL-EVIDENCE-CHECK.json](REAL-EVIDENCE-CHECK.json)。未记录 API Key 或端点地址。

## 实现中修复的问题

- `--version` 最初被命令组要求子命令的行为拦截，已修复并增加回归验证。
- 样例 PDF 最初依赖外部中文语言包，已改为嵌入 TrueType 字体并重新渲染检查。
- 端点返回 HTTP 200 但响应 JSON 损坏或消息结构错误时，SDK 会抛出解码 / 属性异常；已转为安全的退出码 5，不重试、不展示堆栈。
- 非法 BASE_URL 端口在本地检查时拒绝，避免进入 SDK 构造阶段才崩溃。

执行 `uv run python scripts/smoke_ai.py`；正常情况下共 4 次请求。加 `--evidence` 可覆盖新证据字段和本地引文检查。记录日期、模型和结果，不记录 Key。下面保留已有验收基线供回归使用，不表示需要重新验收已完成的 MVP。

- 第一份简历：陈晨、杭州、chen@example.com、电话 null、一条教育经历、三项技能；不能补入不存在的手机号或模型项目经历。
